# WriteLoop 작업 안내

영어 쓰기 연습 앱이다. 질문에 영어로 답하면 LLM이 진단하고, 백엔드가 미션 하나를 골라 다시 쓰게 하는 루프가 핵심이다.

## 대화 규칙

- 사용자에게는 항상 한국어로 답한다. 도구 출력이나 하위 에이전트 보고가 영어여도 마찬가지다.
- 작업을 마치면 커밋까지만 한다. push는 사용자가 "푸시해"라고 할 때만, 쌓인 커밋을 한꺼번에 한다(2026-10-23). `docs/private` 저장소도 같다.
  - main에 push하면 CI가 통과한 뒤 운영에 자동 배포된다(ADR-0015). 그래서 push 시점은 사용자가 정한다.
  - 작업을 보고할 때 push하지 않은 커밋 목록(`git log origin/main..HEAD`)을 알린다.
  - "푸시해"를 받으면 push 전에, 쌓인 커밋 중 마이그레이션·운영 설정 변경이 있는지 알린다.
  - push 뒤에는 CI와 배포(`gh run watch`)를 끝까지 보고, 운영 로그의 Flyway 적용 줄과 `/health`를 확인해 보고한다.
  - CI가 실패하면 배포가 돌지 않아 운영은 그대로다. 원인을 알리고, 고쳐서 다시 push할지 묻는다. 배포나 운영 기동이 실패하면 바로 알리고 장애 대응으로 넘어간다.
  - 문서만 바뀐 push(`docs/**`, `**/*.md`, `.claude/**`)는 CI와 배포가 돌지 않는다.
- 커밋 메시지는 한국어로 쓰고, 기존 형식(`fix:`, `feat:`, `refactor:`, `test:`, `chore:`, `docs:`)을 따르며, 논리 단위로 나눈다.

## 확인 명령 (Windows)

- 백엔드 테스트: `apps/backend`에서 `.\gradlew.bat test`
- 모바일 타입 검사: `apps/mobile`에서 `npm.cmd run typecheck`
- 웹 빌드: 저장소 루트에서 `npm.cmd run build --workspace @english-learning/frontend`
- 채점 규칙 테스트: `node --test scripts/feedback-quality/rules.test.mjs`
- 마이그레이션 확인(Docker 필요): `bash scripts/dev/check-db-migrations.sh --out <저장소 밖 결과 폴더>`
- 문장 피드백 회귀(6건, Docker 필요): `bash scripts/dev/run-llm-smoke.sh --out <저장소 밖 결과 폴더> [--cases <겨냥 케이스 파일>]`
  - 임시 DB로 백엔드를 띄우고 `cases.smoke.json`을 실제 OpenAI로 돌린다. 키는 스크립트가 `.env`에서 꺼내 백엔드에만 넘긴다.
  - OpenAI를 실제로 호출하므로 비용이 든다. 돌리기 전에 `--dry-run`으로 요청 수를 보고, "요청 수(요청당 OpenAI 1~3회, 재시도 포함)"로 사용자에게 알려 승인받는다.
  - 리포트는 케이스 파일마다 `reports/<케이스 파일 이름>/latest.json`에 남는다. `completion` 필드는 줄여서 저장하므로, 스크립트가 피드백 원문(`feedback_diagnosis_logs`)을 결과 폴더에 따로 남긴다.

## 작업 규칙

### 작업 방식

작업 종류에 따라 순서를 정한다. 세 경우 모두 테스트가 먼저이고, 구현은 그 테스트를 통과시키는 일이다. 만든 사람이 자기 결과를 혼자 확인하지 않게 한다.

- 리팩터링(동작은 그대로): 테스트 → 구현 → 같은 테스트 → 검증.
  - 고치기 전에 지금 동작을 테스트로 기록하고, 지금 코드에서 통과하는지 확인한다.
  - 구현은 작은 단계로 나누고, 단계마다 같은 테스트를 돌린다. 구현 중에 테스트를 고쳐서 통과시키지 않는다.
  - 의존성 올리기도 리팩터링으로 다룬다. Spring Boot·Flyway·MySQL 드라이버·Hibernate를 올리면 마이그레이션 확인도 돌린다. Expo나 네이티브 모듈을 올리면 스토어 빌드가 필요하다고 보고한다.
- 새 기능: 명세 → 테스트 작성 → 구현 → 검증.
  - 명세에 화면 동작, API, 예외 상황을 적고 사용자에게 확인받는다. 웹·모바일 양쪽 반영과 LLM 출력·비용 변화도 적는다.
  - 테스트는 구현보다 먼저, 명세만 보고 쓴다. 이 시점에는 기능이 없으니 테스트가 실패하는 것이 맞다.
  - 구현은 명세를 따르고, 먼저 써 둔 테스트를 통과시킨다. 테스트를 구현에 맞춰 고치지 않는다. 명세가 틀렸으면 명세부터 고치고 사용자에게 알린다.
  - 검증은 명세와 결과를 비교해 빠진 것과 명세에 없는 것을 찾는다.
- 버그 수정: 재현 테스트 → 수정 → 통과 확인.
  - 재현 테스트가 지금 코드에서 실패하는지 먼저 확인한다. 실패하지 않으면 원인을 다시 찾는다.
- 질문, 설명, 조사만 할 때는 이 작업 방식과 backlog 확인을 따르지 않는다. 답하다가 고칠 것을 찾으면 고치기 전에 묻는다.
- 검증은 구현 과정을 모르는 별도 에이전트가 변경분(diff), `runner`의 실행 기록, 저장소 코드를 보고 한다.

#### 규모

규모는 줄 수가 아니라 바뀌는 곳으로 정하고, 시작할 때 사용자에게 확인받는다. 애매하면 중간으로 한다.

- 작은 수정: 화면 문구, 문서, 주석만 바꾼다. 혼자 한다.
- 중간: 다음 중 하나라도 바뀐다. 혼자 테스트와 구현을 하고, 실행 확인(`runner`)과 검증(`verifier`)은 별도 에이전트에 맡긴다.
  - 백엔드 동작 코드, 웹·모바일 동작 코드(화면 문구만 바꾸는 것은 제외)
  - LLM 프롬프트·스키마·모델(문구 한 줄이라도)
  - DB 스키마
  - API 요청·응답
  - 운영 설정(`infra/nginx`, `docker-compose*.yml`, `.github/workflows`, `scripts/ops`, `application*.yml`)
  - 의존성
  - 채점 규칙과 검사 도구(`scripts/feedback-quality`, `scripts/run-feedback-quality-check.mjs`, `scripts/dev`), Claude 설정(`.claude/hooks`, `.claude/settings.json`)
- 큰 작업(여러 화면에 걸친 기능, 큰 리팩터링): 역할을 나눠 진행할지 사용자에게 먼저 묻는다. 에이전트 여러 개를 쓰면 비용이 몇 배로 든다.
  - 큰 기능은 따로 확인할 수 있는 작은 기능으로 나눠, 하나씩 명세 → 테스트 → 구현 → 검증을 돈다. 나누는 방법은 명세 단계에서 사용자와 정한다.
- 작업 지침(`.claude/CLAUDE.md`, `.claude/agents/*.md`) 변경은 위 공정을 따르지 않는다.
  - 규칙이나 절차가 바뀌면 메인 세션이 고치고 `instruction-reviewer`에 검토를 맡긴다. 변경분(새로 만든 지침 파일은 `git add -N`을 한 뒤 `git diff`해야 들어간다), 변경의 목적, "사용자와 이미 정한 내용" 목록을 작업 폴더에 두고 폴더 경로를 넘긴다.
  - 검토 보고의 칸마다 이렇게 한다.
    - 정한 내용과 다름: 고치기 전에 사용자에게 묻는다.
    - 확실한 문제, 의심 가는 문제: 메인 세션이 고친다. 다만 메인 세션이 그 지적에 동의하지 않으면, 고치지 말고 근거를 붙여 사용자에게 묻는다. 고치는 방법이 정한 내용을 바꾸는 경우는 아래 "에이전트"의 규칙을 따른다.
    - 미확인: 메인 세션이 돌려 보고 결과를 적는다. 돌려 볼 수 없으면 사용자에게 알린다.
    - 추천(자세한 추천, 한 줄 추천 모두): 정한 내용을 바꾸든 아니든, 문구만 바꾸는 추천이어도 반영하지 않고 사용자에게 보인다. 사용자가 고른 것만 반영한다(2026-10-25 사용자 결정). 사용자가 무엇을 고르고 버렸는지는 다음 번호의 `NN-decision.md`로 남긴다.
    - 검토 결과를 사용자에게 알릴 때 "그 밖의 추천"(한 줄 추천)도 요약하거나 빼지 않고 원문 그대로 보인다.
  - 지침에 새 명령을 적었으면 그 명령을 한 번 실제로 돌려 본다. 비용이 드는 명령(OpenAI 호출)은 `--dry-run`까지만 하고, 실제 실행은 사용자 승인 뒤에 한다.
  - 문구만 다듬는 변경은 혼자 한다. 검토에서 나온 추천은 문구 수정이어도 위 추천 규칙을 따른다.
  - 검토 자료는 작업 폴더(`C:/WriteLoop-work/<날짜>-instr-<짧은 이름>/`)에 남긴다. `01-purpose.md`(변경의 목적과 이미 정한 내용, 메인 세션), `02-diff.txt`(새로 만든 지침 파일 포함, 메인 세션), `03-review.md`(검토 보고를 메인 세션이 그대로 저장), 사용자의 선택(추천 선택, 아래 "에이전트"의 규칙에 따라 물은 것의 답)을 남긴 결정 파일(`NN-decision.md`, 메인 세션). 기준 커밋은 첫 변경 전의 HEAD로 `02-diff.txt` 첫 줄에 적고, 변경분은 언제나 `git diff <기준 커밋> -- .claude`(커밋하지 않은 변경 포함)로 만든다. 중간에 커밋해도 앞의 변경이 빠지지 않게 하려는 것이다. 고친 뒤 다시 검토하면 그 전체 변경분을 다음 번호로 이어 붙이고, 다시 폴더 경로를 넘긴다. 검토자는 폴더의 파일을 번호 순서로 모두 읽는다.
- DB 스키마 변경은 크기와 관계없이 `runner`의 마이그레이션 확인과 `verifier` 검증을 둔다. 운영 설정 변경도 크기와 관계없이 검증을 따로 둔다(2026-10-24 V110 사고).

#### 작업 폴더

중간 규모부터는 단계를 맡은 쪽이 자기 결과 파일을 남기고, 다음 단계에는 그 파일을 넘긴다. 작업 지침 변경의 검토 자료도 같은 폴더 규칙으로 남긴다(위 "규모"의 작업 지침 변경). 진행 상태가 대화에만 있으면 대화가 요약되거나 새 세션이 열릴 때 사라지기 때문이다.

- 파일은 저장소 밖 `C:/WriteLoop-work/<날짜>-<짧은 이름>/`에 생긴 순서대로 번호를 붙여 모은다.
- 공통 상태 파일은 두지 않는다. 폴더의 파일 목록이 곧 진행 상태다.
- 작업 폴더는 지우지 않는다. 정리는 사용자가 직접 한다(2026-10-25 사용자 결정).
- 보통의 순서와 쓰는 쪽:
  - `01-spec.md`(메인 세션): 작업 종류, 확인받은 입력 원문(새 기능은 명세, 버그 수정은 재현 상황, 리팩터링은 범위와 목적, 장애는 원인과 증상. 장애 수정의 작업 종류는 버그 수정이다), 사용자가 확인한 규모, 기준 커밋 SHA
  - `02-tests.md`(테스트를 쓴 쪽): 만든 테스트, 가정한 것, 겨냥 회귀 케이스의 sha256
  - `02-cases-target.json`(테스트를 쓴 쪽): 문장 피드백 LLM을 바꿀 때의 겨냥 회귀 케이스
  - `03-runner-test/`(`runner`): 테스트 커밋 시점 기록. 각 파일 첫 줄의 HEAD가 테스트 커밋이다
  - `04-impl.md`(구현한 쪽): 명세를 어떻게 해석해 무엇을 바꿨는지. `verifier`는 읽지 않는다
  - `05-runner-impl/`(`runner`): 구현 커밋 시점 기록
  - `06-diff-all.txt`, `06-diff-tests.txt`(메인 세션): `verifier`에 넘기는 변경분
  - `07-verify.md`(`verifier`)
- 중간에 생긴 사용자 결정(비용 승인, 테스트 수정 허락)이나 단계를 건너뛴 이유는, 그 시점의 다음 번호로 메인 세션이 `NN-decision.md`를 남긴다. 결정 파일에는 사용자 결정, 대상, 사용자에게 보인 이유만 적는다. 구현에 관한 설명은 `-impl.md`나 `-fix.md`에 둔다(`verifier`가 결정 파일은 읽는다).
- 구현 쪽의 설명 파일은 이름을 `-impl.md`, `-fix.md`로 끝낸다. `verifier`가 읽지 않을 파일을 이름으로 가리기 위해서다.
- 한 번 쓴 파일은 고치지 않는다. 고친 뒤 다시 돌면 다음 번호로 이어 붙인다(예: `08-fix.md`, `09-runner-fix/`, `10-diff-all.txt`, `10-diff-tests.txt`, `11-verify.md`). 다시 검증할 때도 새 커밋 기준으로 변경분을 다시 만든다.
- 각자 자기 파일만 쓴다. `verifier`는 파일을 쓸 수 없으니 메인 세션이 그 보고를 그대로 저장한다.
- 다음 에이전트에는 내용을 옮겨 말하지 않고 파일 경로를 넘긴다. 명세는 `01-spec.md`를 넘긴다.
- 새 세션이거나 대화가 요약됐으면 이 폴더의 파일을 번호 순서로 읽고 이어서 한다. 명세를 기억으로 다시 쓰지 않는다.

#### 커밋 순서(중간 규모부터)

push는 위 규칙대로 요청받았을 때만 한다.

1. 테스트를 구현 전에 따로 커밋한다(`test:`). 실패하는 테스트 커밋만 있고 구현이 없는 상태로는 push하지 않는다.
2. 바로 `runner`로 그 테스트만 돌려 테스트 커밋 시점의 결과를 남긴다. 새 기능·버그 수정은 실패, 리팩터링은 통과여야 한다.
3. 구현을 커밋한 뒤 `runner`를 돌린다. 커밋 번호 하나로 어떤 코드를 돌린 기록인지 정해지게 하려는 것이다.

- `runner`를 부르기 전에 `git status --short`가 비어 있어야 한다.
- 단위 테스트로 확인할 수 없는 변경(마이그레이션만, 운영 설정, 프롬프트 문구, 의존성 버전만)은 1·2번을 건너뛴다. 대신 커밋한 뒤 `runner`로 변경 종류별 확인(마이그레이션 확인, 문법 검사, LLM 회귀, 전체 테스트)을 돌린다. 건너뛴 이유는 결정 파일(`NN-decision.md`)로 남긴다.

#### 에이전트(`.claude/agents/`)

메인 세션은 사용자와 대화하며 명세를 쓰고, 에이전트에 일을 나눠 주고, 결과를 모아 커밋·backlog·보고를 한다. 하위 에이전트는 운영에 접속하지 않는다.

- `test-writer`: 큰 작업에서 테스트를 쓴다. 중간 규모에서는 메인 세션이 쓴다.
- `implementer`: 큰 작업에서 구현한다. 중간 규모에서는 메인 세션이 구현한다.
- 두 에이전트에는 확인받은 명세 원문(`01-spec.md`)을 넘긴다. `test-writer`에는 구현 계획을 넘기지 않는다.
- 둘 중 하나가 명세 문제로 멈추면, 메인 세션이 사용자에게 묻고 다시 맡긴다.
- `runner`: 테스트, 빌드, 마이그레이션 확인, LLM 회귀, 설정 문법 검사, 로컬 API 호출을 실행하고 기록을 남긴다. 구현한 쪽이 자기 확인 기록을 만들지 않게 하려는 것이다.
  - 결과 폴더는 작업 폴더 아래에 실행마다 새로 준다(예: `03-runner-test/`, `05-runner-impl/`). 한 번에 하나만 돌린다.
  - 바뀐 영역만 맡긴다. 백엔드가 바뀌면 백엔드 테스트, 웹이면 웹 빌드, 모바일이면 타입 검사와 lint를 돌린다. 나머지는 push 때 CI가 막는다.
  - CI에 없는 확인(마이그레이션, 모바일 lint, LLM 회귀, 설정 문법, 로컬 API 호출)은 해당하면 꼭 `runner`로 돌린다.
  - 환경 문제(Docker 꺼짐, 포트 사용 중, 빌드 폴더 잠금)로 실행하지 못하면, 원인을 사용자에게 알리고 해결한 뒤 다시 돌린다. 실행하지 못한 확인을 통과로 보고하지 않는다.
  - 마이그레이션이 든 커밋은 마이그레이션 확인이 모두 OK가 되기 전에는 push하지 않는다.
- `verifier`: 읽기만 한다. 파일을 하나씩 고르지 않고 작업 폴더 경로를 넘긴다. 메인 세션이 고르다 빠뜨리는 파일이 없게 하려는 것이다.
  - 넘기기 전에 메인 세션이 변경분 두 개를 만들어 폴더에 둔다.
    - 전체 변경분(`NN-diff-all.txt`): `git diff <기준 커밋>..HEAD`. 첫 줄에 기준 커밋, HEAD, 명령을 적는다.
    - 테스트 변경분(`NN-diff-tests.txt`): `git diff <테스트 커밋>..HEAD -- apps/backend/src/test scripts/feedback-quality scripts/run-feedback-quality-check.mjs scripts/dev`. 첫 줄에 테스트 커밋, HEAD, 명령을 적는다. 테스트 커밋이 없는 작업(커밋 순서 1·2번을 건너뛴 경우)은 만들지 않는다.
  - `verifier`는 폴더의 파일을 번호 순서로 모두 읽되, 구현 쪽의 설명(`-impl.md`, `-fix.md`)은 읽지 않는다. 코드는 변경분과 저장소에서 직접 읽는다.
  - 다시 검증할 때는 가장 최근 번호의 변경분과 `runner` 기록을 기준으로 판단한다. 앞 검증 보고는 지적이 고쳐졌는지 보는 데 쓴다.
- `instruction-reviewer`: 작업 지침 변경을 검토한다(위 "규모"의 작업 지침 변경). 읽기만 하고, 문제와 더 나은 방안을 보고한다.
- `runner`나 `verifier`가 도는 동안에는 저장소 파일을 고치지 않고 끝날 때까지 기다린다.
- 검증에서 나온 문제를 고치면, 고친 것을 커밋하고 `runner`로 다시 실행한 뒤 고친 부분을 다시 검증받는다.
- `verifier`의 지적에 동의하지 않으면 혼자 넘기지 않는다. 근거(코드 위치, 실행 기록)를 붙여 사용자에게 보고하고 결정받는다.
- `verifier`나 `instruction-reviewer`의 지적을 고치는 방법이 사용자와 정한 내용을 바꾸면, 고치기 전에 사용자에게 묻는다. 지적이 맞아도 그렇다.
  - 정한 내용: 사용자에게 확인받은 명세(이번 작업의 `01-spec.md` 포함), 결정 파일, 지침 검토의 `01-purpose.md`에 적은 정한 내용, 이번 작업 전부터 있던 지침(`.claude/CLAUDE.md`, `.claude/agents/*.md`)의 규칙(날짜가 없는 것 포함)
  - 바꾼다: 위의 것을 뒤집거나 다르게 바꾸는 것. 이번 작업에서 새로 넣은 줄을 고치는 것, 기존 규칙과 부딪히지 않는 줄을 더하는 것, 명세대로 코드를 고치는 것은 해당하지 않는다(2026-10-25, 검토의 제안을 따라 정한 설계와 다른 공통 상태 파일을 넣었다가 되돌린 일).
  - 물어서 받은 답은 다음 번호의 `NN-decision.md`로 남긴다.
- 같은 문제로 고침과 검증을 두 번 돌아도 풀리지 않으면 멈추고, 시도한 것과 남은 문제를 사용자에게 보고한다.
- 테스트 수정은 사용자가 결정한다. 결정하면 결정 파일(`NN-decision.md`)로 남기고 `test:` 커밋으로 따로 남긴다. 그 파일은 작업 폴더에 있으므로 `verifier`가 읽는다.

#### 변경 종류별로 더 할 것

- 문장 피드백 LLM(프롬프트·스키마·모델·미션 선택)을 바꾸면 6건 회귀(`scripts/dev/run-llm-smoke.sh`)를 돌린다.
  - 이번 변경을 겨냥한 회귀 케이스를 구현 전에 작업 폴더에 `02-cases-target.json`으로 10건 이하로 쓴다(큰 작업은 `test-writer`). 6건 세트와 합친 요청 수가 16을 넘으면 두 번에 나눠 돌린다(시간 제한). 형식은 `scripts/feedback-quality/cases.smoke.json`과 같다. 쓴 직후 파일의 sha256 전체를 `02-tests.md`에 적고, 사용자에게도 대화로 알린다. 구현 뒤에 케이스를 고쳐 통과시키지 못하게 하려는 것이다. 중간 규모에서는 케이스와 구현을 메인 세션이 모두 쓰므로, 사용자가 본 값이 기준이 된다.
  - 메인 세션이 요청 수(`--dry-run`, 케이스 파일을 모두 합친 수)를 사용자에게 알리고 승인받은 뒤, `runner`가 겨냥 케이스와 6건 세트를 함께 돌린다.
  - `verifier`는 원본 리포트와 피드백 원문(`feedback-diagnosis-logs.tsv`)을 본다. 최종 보고에는 실제 응답 몇 개를 붙여 사용자도 보게 한다.
  - 6건 세트는 채점 규칙을 정리하기 전까지 알려진 실패 유형이 셋 있다. 이 셋은 따로 표시하고, 그 밖의 실패만 문제로 본다.
    - 지금은 만들지 않는 `coachMove.successCheck`를 검사해서 생기는 실패
    - 새로 끼워 넣는 문법 교정에 `before`가 없어서 생기는 실패
    - 필수 요소를 다 쓴 짧은 답을 COMPLETE로 끝내서 생기는 실패
- 코치, 영어일기, Now in English의 LLM을 바꾸면, 아직 회귀 세트도 키를 넣어 부를 스크립트도 없다(일기 평가셋은 backlog). 사용자가 개발 앱에서 직접 불러 보고 판단한다. 최종 보고에 확인할 화면과 입력 예를 "사용자가 직접 볼 것"으로 적는다.
- `application*.yml`이나 빈 구성(설정 클래스, 생성자 의존성)이 바뀌면 `runner`가 `check-db-migrations.sh`로 백엔드가 실제로 뜨는지 본다. 단위 테스트도 CI도 백엔드를 띄우지 않아서, 설정 오류는 운영 첫 기동에서야 드러난다.
- 웹·모바일 화면 변경은 테스트 도구가 없으니, 명세에 확인 목록(화면, 조작, 기대 결과)을 적는다.
  - 최종 보고에 이 목록과 `verifier`의 의심·미확인 항목을 "사용자가 직접 볼 것"으로 넘긴다.
  - 화면 버그는 재현 절차를 적는다. 재현 테스트를 못 쓰면 그 이유를 보고한다.
- 운영 설정 변경은 `runner`가 문법을 확인한다: compose는 `docker compose config -q`, 워크플로는 actionlint 컨테이너, `scripts/ops/*.sh`는 `bash -n`, nginx는 가능하면 `nginx -t`.
  - `deploy.yml`을 바꾸면, 보고에 서버에서 `scripts/ops/deploy.sh`를 직접 돌리는 비상 롤백 방법을 적는다. 이 파일이 깨지면 Actions의 롤백도 같이 깨진다.
- Claude 설정(`.claude/hooks`, `.claude/settings.json`)을 바꾸면 `runner`가 훅의 파이썬 문법(`ast.parse`, 캐시 파일을 남기지 않는다)과 JSON 문법을 확인한다. `.claude/**`만 바뀐 push는 CI가 돌지 않는다.
- 로컬 API 호출(`check-db-migrations.sh --api`)은 로그인 없는 API만 부를 수 있다. 로그인이 필요한 API는 백엔드 단위 테스트로 확인한다.

### DB

- 스키마 변경은 Flyway로 한다. `apps/backend/src/main/resources/db/migration`에 다음 버전의 `V번호__설명.sql`을 추가한다(ADR-0013).
- 이미 푸시한 마이그레이션은 고치지 않는다. Flyway 체크섬이 어긋나 기동이 막히고, Claude 훅도 수정을 막는다.
- `infra/mysql/schema`는 107번에서 동결했다. 새 파일을 넣지 않는다.
- JPA는 `ddl-auto: validate`다. Flyway가 먼저 마이그레이션을 적용한 뒤 엔티티와 DB 구조를 검사하고, 다르면 서버가 뜨지 않는다. 엔티티를 바꾸면 마이그레이션을 같은 커밋에 만든다.
- 운영에서 마이그레이션은 배포 후 첫 기동 때 자동 적용되므로, 배포 전에 백업한다.
- 컬럼 삭제처럼 이전 코드와 호환되지 않는 변경은 두 번의 배포로 나눈다.
- 열을 지우거나 이름을 바꾸기 전에 그 열을 쓰는 뷰가 있는지 확인한다. MySQL에는 뷰가 쓰는 열 목록이 없으니 `information_schema.VIEWS`의 `VIEW_DEFINITION`과 마이그레이션 파일의 `VIEW` 정의에서 열 이름을 찾는다. 깨진 뷰가 있으면 배포 전 DB 백업(mysqldump)이 실패해 배포가 멈춘다(2026-10-24, V111).
- 마이그레이션을 추가하면 `scripts/dev/check-db-migrations.sh`로 확인한다. 임시 컨테이너에서 빈 DB(`V107__baseline.sql`부터)와 기존 DB(기준선 107) 양쪽으로 백엔드를 띄우고, 뷰가 조회되는지와 운영 배포와 같은 방식의 백업(mysqldump)이 성공하는지 본다.
  - 백업까지 보는 이유: 운영 배포는 마이그레이션 전에 백업하므로, 마이그레이션이 뷰를 깨뜨려도 그 배포는 통과하고 다음 배포의 백업에서야 드러난다(2026-10-24, V111).

### LLM 요청

- 구조화 출력은 스키마의 키 순서대로 생성된다. 순서는 동작에 영향을 주므로, 순서를 바꿀 때는 회귀 테스트를 함께 돌린다.
- LLM 스키마와 프롬프트는 `OrderedMaps`나 `LinkedHashMap`으로 만든다. `Map.of`, `Map.ofEntries`, `Map.copyOf`, `Set.of`는 JVM을 시작할 때마다 순서가 바뀐다. `LlmRequestDeterminismTest`가 검사한다.
- 화면에 쓰지 않는 내용을 LLM에 생성시키지 않는다. 출력 토큰이 곧 응답 시간이고 비용이다.
- LLM이 실패했을 때 학습자 입력과 무관한 고정 문구를 AI 결과처럼 보여 주거나 저장하지 않는다. 솔직한 안내 오류를 돌려준다. 질문의 힌트처럼 그 상황에 맞는 데이터로 만든 대체 응답(코치 도움)은 괜찮다.
- 서버 시간 제한은 앱 시간 제한보다 짧아야 한다. 앱은 피드백·일기 90초, 코치·Now in English 45초에서 끊고, nginx는 85초에서 끊는다.
- LLM 호출은 요청 단위 마감(`LlmRequestDeadline.within`) 안에서, DB 트랜잭션 밖에서 한다(ADR-0016). OpenAI 호출은 `OpenAiStructuredOutputSupport.buildResponsesRequest`를 거쳐야 마감을 따른다.
- 문장 피드백(`CanonicalFeedbackContract`, `FeedbackLearningContractPolicy`, `CanonicalFeedbackAssembler`)을 바꾸기 전에 `.agents/skills/writeloop-feedback-logic/SKILL.md`와 `references/feedback-schema.md`를 읽는다.
  - 사용자가 이 두 문서를 새로 쓰기로 해서, 그때까지는 읽기만 하고 갱신하지 않는다(2026-10-25 사용자 결정).
  - 코드와 문서가 달라진 곳은 보고에 적고, backlog의 6건 회귀 채점 규칙 정리 항목(스킬 문서를 새로 쓸 때 함께 하는 일)에 덧붙인다. 문서와 확인받은 명세가 다르면 명세를 따른다.
  - 문서의 검증 절차(Verification 절, `references/regression-workflow.md`) 대신 이 파일의 작업 방식을 따른다. 6건 회귀는 "변경 종류별로 더 할 것"의 조건(문장 피드백 LLM을 바꿀 때)에만 돌린다.

### 설정

- 새 환경 변수는 `docker-compose.yml`의 `environment:`에도 추가한다. 이 파일은 `env_file`을 쓰지 않아서, 목록에 없는 변수는 컨테이너에 전달되지 않는다.

### 웹과 모바일

- 응답 구조를 바꾸면 웹(`apps/frontend/lib/types.ts`)과 모바일(`apps/mobile/src/lib/types.ts`) 타입을 함께 바꾼다.
- 기능은 두 화면에 맞춰 넣는다.
- API 요청·응답은 스토어에 나가 있는 모바일 버전과 호환되게 바꾼다. 서버는 push하면 바로 바뀌지만, 사용자 폰의 옛 앱은 업데이트할 때까지 그대로다.
  - 응답 필드는 추가만 한다. 옛 앱은 모르는 필드를 무시한다.
  - 요청 필드는 선택으로만 추가하고 서버에 기본값을 둔다. 옛 앱은 새 필드를 보내지 않는다.
  - 응답의 enum 값(미션 종류 등)을 추가하면, 옛 앱이 모르는 값을 받았을 때 어떻게 되는지 확인한다. 모르는 필드와 달리 화면이 깨질 수 있다.
  - 필드를 지우거나 이름·의미를 바꾸는 일은, 새 필드를 쓰는 앱을 스토어에 내보내고 최소 지원 버전(`APP_VERSION_*_MINIMUM_SUPPORTED`)을 올린 뒤의 배포에서 한다. 열 삭제를 배포 두 번으로 나누는 것과 같다.
  - 새 API를 쓰는 모바일 기능은 서버 배포(push)가 끝난 뒤 스토어 빌드를 만든다. 빌드는 커밋된 깨끗한 상태에서 하고, 보고에 커밋 SHA를 적는다.

## 운영과 비밀 정보

- 운영 서버 접속과 운영 DB 조회는 메인 세션이 권한 모드와 관계없이 할 수 있다(2026-10-22, ADR-0012). 하위 에이전트는 운영에 접속하지 않는다.
- 배포, 마이그레이션 적용, 설정 변경처럼 운영을 바꾸는 작업은 사용자가 요청했을 때 하고, DB를 바꾸기 전에는 백업한다.
- `env_files/`, `.env`, `*.pem`, 서비스 계정 JSON 같은 비밀 파일은 내용을 출력하지도, 읽지도 않는다. 필요하면 변수 이름만 확인한다.
- 배포(ADR-0015):
  - main push → GitHub Actions가 테스트하고 이미지를 GHCR에 올린 뒤, `deploy.yml`이 서버에서 `scripts/ops/deploy.sh`를 실행한다.
  - `deploy.sh`가 DB 백업, 이미지 받기, 재시작, 기동 확인을 한다. Flyway 마이그레이션은 백엔드가 기동할 때 적용된다.
  - 재배포·롤백은 Actions의 `Deploy` 워크플로를 커밋 SHA로 직접 실행한다. CI가 이미지를 올린 커밋만 된다.
  - 운영 서버에서 `docker compose build`나 `up --build`를 하지 않는다. 메모리가 모자라 서버가 멈춘다(2026-10-22 장애).
  - `deploy.sh`는 Redis를 다시 만들지 않는다. 모바일 로그인 유지 토큰이 Redis에만 있으니 Redis 볼륨을 지우지 않고, Redis 설정 변경은 README 절차로 직접 적용한다.
  - 운영 DB 조회는 서버에서 `bash scripts/ops/prod-db.sh mysql writeloop -e "..."`로 한다.
- 장애 대응:
  - 먼저 운영 로그와 DB를 조회해 원인을 확인한다. 사용자에게 선택지(직전 SHA로 롤백, 수정 배포, 운영 DB 직접 조치)와 각각의 위험을 알리고, 사용자가 고른 뒤 조치한다.
  - 롤백해도 DB는 돌아가지 않는다. 롤백 전에 그 사이 적용된 마이그레이션이 롤백할 코드와 맞는지 본다. 열을 지운 뒤라면 이전 코드는 `ddl-auto: validate`에 걸려 뜨지 않는다.
  - 배포 전 백업이 실패하면 롤백 배포도 같은 자리에서 멈춘다(`deploy.sh` 1단계). 백업을 막는 원인(깨진 뷰 등)을 운영 DB에서 직접 고칠지 묻는다. 직접 고쳤으면 같은 결과를 내는 마이그레이션으로 남기되, 이미 고친 운영에서도 실패하지 않게 쓴다(2026-10-24, V111).
  - 수정 배포에서도 재현 테스트와 마이그레이션 확인은 지킨다. 메인 세션이 장애 원인과 증상을 `01-spec.md`에, 고친 과정을 `-fix.md`에 남기고, `verifier`에는 작업 폴더 경로를 넘겨 바로 돌린다.
  - 장애 중에는 LLM 회귀와 바뀐 영역 밖의 `runner` 항목을 생략할 수 있다. 생략한 확인은 backlog에 적고 장애가 끝난 뒤 한다.
- 모바일 앱은 서버 배포와 별도로 스토어에 배포해야 반영된다. 스토어 빌드 전 버전 규칙은 피드백 로직 스킬 문서의 "Mobile Store Build Guardrail"을 따른다.
