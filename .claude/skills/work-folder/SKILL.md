# 작업 폴더


중간 규모부터는 단계를 맡은 쪽이 자기 결과 파일을 남기고, 다음 단계에는 그 파일을 넘긴다. 작업 지침 변경의 검토 자료도 같은 폴더 규칙으로 남긴다(`instruction-change` 스킬). 진행 상태가 대화에만 있으면 대화가 요약되거나 새 세션이 열릴 때 사라지기 때문이다.

- 파일은 `private/work/<순번>-<날짜>-<한국어 이름>/`에 생긴 순서대로 번호를 붙여 모은다. 다른 컴퓨터에서도 이어서 할 수 있게 비공개 저장소에 둔다(2026-10-25 사용자 결정).
  - 폴더는 `bash scripts/dev/work.sh new <한국어 이름>`으로 만든다(지침 변경은 `--instr`, 큰 기능의 자식 폴더는 `--parent <부모 폴더>`). 이름 규칙에 맞는 번호와 날짜를 붙이고, 01 뼈대 첫 줄에 두 저장소의 지금 HEAD를 기준 커밋으로 적는다(자식 폴더는 날짜 없이 두 자리 번호만 붙고, 기준 커밋은 첫 줄의 부모 줄 다음 줄에 적힌다). 그래서 폴더는 첫 변경을 커밋하기 전에 만든다. 이미 커밋했으면 01의 기준 커밋을 첫 변경 전 HEAD로 고쳐 적는다. 폴더 안의 다음 번호는 `bash scripts/dev/work.sh next <폴더>`로 본다.
  - 단계 파일(명세, 보고, 결정, 검증 보고, runner의 `summary.txt`, 겨냥 케이스)은 `private`에서 커밋한다. 큰 원본 기록(runner 폴더의 나머지 파일, 변경분 `*-diff*.txt`)은 `private/.gitignore`로 빼서 그 컴퓨터에만 남는다.
  - 예외로 LLM 회귀의 `latest.json`(채점 결과)과 `feedback-diagnosis-logs.tsv`(피드백 원문)는 커밋한다. 다시 돌리면 비용이 들고 같은 결과가 나오지 않는 기록이라, 다른 컴퓨터에서도 원문을 보고 나중에 품질 변화를 비교할 수 있게 하려는 것이다(2026-10-25 사용자 결정). 같은 내용인 시각이 붙은 리포트 사본은 빼고, 실행 순서는 runner 폴더 번호로 안다.
  - 작업 폴더에 단계 파일이 생기면(하위 에이전트가 쓴 것 포함) 그 단계가 끝나 다음 단계로 넘기기 전에 메인 세션이 `private`에서 커밋한다. runner나 verifier가 도는 동안에는 커밋하지 않는다. 검토 대상인 파일(예: 지침 검토 중인 `private/.gitignore`)은 검토가 끝난 뒤 검토 보고와 함께 커밋한다. 커밋이 늦으면 다른 컴퓨터로 옮길 것이 없다.
  - 변경분은 커밋된 파일에 적힌 커밋 번호로 `bash scripts/dev/work.sh diff <폴더>`가 다시 만든다. 기준 커밋은 `01-main-spec.md`(지침 변경은 `01-main-purpose.md`), 테스트·구현 커밋은 runner 폴더의 `summary.txt`에 있다.
    - 일반 작업은 기준 커밋부터 끝 커밋까지 만든다. 끝 커밋은 구현 기록(`-runner-test`가 아닌 runner 기록)이 있으면 종류와 관계없이(구현 뒤에 더한 테스트 기록 포함) 번호가 가장 큰 runner 기록의 커밋이고, 아직 없으면 지금 HEAD다. 그래서 뒤에 다른 작업의 커밋이 쌓이거나 다른 컴퓨터에서 다시 만들어도 runner 기록과 같은 코드를 가리킨다.
    - 다른 끝 커밋이 필요하면 `--head <커밋>`을 준다. `--head`는 끝 커밋만 바꾸고, 테스트 커밋은 그대로 번호가 가장 큰 `-runner-test` 기록에서 읽는다. 그 테스트 커밋보다 앞 커밋을 주면 테스트 변경분이 거꾸로 나와 더한 테스트가 지운 것처럼 보이므로, verifier에 넘길 변경분에는 `--head`를 주지 않는다.
    - 지침 변경의 변경분은 `instruction-change` 스킬대로 만든다.
  - 다른 컴퓨터에서 이어서 할 때는 빠진 것 중 다시 만들 수 있는 것만 다시 만든다. 변경분은 다음 번호로 다시 만들고, 테스트·빌드·DB 확인의 원본 기록이 필요하면 runner를 다시 돌린다(새 번호). LLM 회귀는 커밋된 `summary.txt`, `latest.json`, `feedback-diagnosis-logs.tsv`로 판단하고, 원본 기록이 빠졌다는 이유로 다시 돌리지 않는다.
  - 다른 컴퓨터에서 이어서 하려면 `private`를 push해야 한다. push는 다른 push처럼 사용자가 요청할 때 한다. `private` push는 운영 배포와 상관없다.
  - 옮겨지는 것은 작업 기록뿐이다. 공개 저장소의 코드는 main에 push(= 운영 배포)해야 옮겨진다. 실패하는 테스트 커밋만 있는 단계에서는 push할 수 없으니, 그 단계에서는 코드를 다른 컴퓨터로 옮길 수 없다.
- 새 폴더를 만들지 이어 붙일지: 그 작업 안에서 생긴 후속 결정과, 그 작업에서 나온 검증·검토 지적의 고침은 그 작업 폴더에 다음 번호로 이어 붙인다. 목적이 새롭거나, 끝난(검증·검토를 마치고 사용자에게 보고한) 작업에서 나중에 나온 버그 수정이나 변경이면 새 작업 폴더를 만든다. 옛 폴더에 이어 붙이면 옛 명세와 옛 기준 커밋을 쓰게 되기 때문이다. 다만 지침 변경에서 고른 추천이 모두 문구만 바꾸는 경우는 `instruction-change` 스킬의 규칙을 따른다.
- 큰 기능을 작은 기능으로 나눴으면(`work-process` 스킬의 "작업 방식"), 큰 기능의 작업 폴더 안에 작은 기능마다 자식 폴더를 만든다(2026-10-25 사용자 결정).
  - 부모 폴더는 `private/work/` 바로 아래에 있는 작업 하나의 맨 위 폴더다. 자식 폴더를 쓰면 작업 지침(CLAUDE.md, `.claude/skills/`)과 에이전트 지침에서 말하는 "작업 폴더"는 그 자식 폴더를 말한다. 부모 폴더의 파일(전체 명세, 결정 파일)은 함께 읽는다.
  - 부모 폴더에는 큰 기능 전체의 명세와 나누는 계획(`01-main-spec.md`), 전체에 걸친 결정 파일을 둔다.
  - 자식 폴더 이름은 `NN-<한국어 작은 기능 이름>/`(두 자리 번호)이다. 이 번호는 부모 폴더의 파일 번호와 한 순번으로 매긴다(예: `01-main-spec.md`, `02-main-decision.md`, `03-목록/`, `04-필터/`). 그 안에서 명세 → 테스트 → 구현 → 검증을 한 바퀴 돈다. 파일 번호는 자식 폴더 안에서 01부터 매긴다.
  - 자식 폴더의 `01-main-spec.md` 첫 줄에는 부모 폴더 경로와, 부모의 나누는 계획 중 어느 항목인지 적는다(예: `부모: private/work/012-2026-10-26-저장표현-검색/ · 계획 ① 목록`). test-writer가 테스트할 범위를 이 항목으로 안다.
  - 자식 폴더 이름은 `NN-runner-`로 시작하지 않는다. `private/.gitignore`가 그 이름을 runner 결과 폴더로 보고 원본 기록처럼 뺀다.
  - 에이전트에는 자식 폴더 경로를 넘긴다. test-writer, verifier는 자식 폴더와 함께 부모 폴더의 파일(다른 자식 폴더는 빼고)도 읽는다.
  - 그 밖의 작업은 폴더 하나로 한다.
- 이름 규칙(2026-10-25 사용자 결정):
  - 작업 폴더: `<순번>-<날짜>-<한국어 이름>/`. 순번은 세 자리이고, 날짜와 관계없이 전체 작업에 이어서 매긴다. 새 폴더는 `private/work/`에서 가장 큰 순번 다음 번호를 쓴다. 지침 변경은 `<순번>-<날짜>-지침-<한국어 이름>/`이다. 예: `011-2026-10-25-지침-작업폴더-이름규칙/`.
  - 안의 파일과 runner 결과 폴더: `<순번>-<작성한 쪽>-<종류>.<확장자>`. 이 순번은 작업 폴더 안의 두 자리 번호다(작업 폴더의 세 자리 순번과 다르다. `private/.gitignore`가 두 자리 번호로 runner 폴더를 가린다). 작성한 쪽은 `main`(메인 세션), `test-writer`, `runner`, `verifier`, `instruction-reviewer`다. 예: `01-main-spec.md`, `02-test-writer-tests.md`, `03-runner-test/`, `04-main-impl.md`, `07-verifier-verify.md`, `03-instruction-reviewer-review.md`, `NN-main-decision.md`.
  - 구현은 늘 메인 세션이 하므로 구현 설명의 작성한 쪽은 `main`이다(예: `04-main-impl.md`). 중간 규모처럼 메인 세션이 테스트를 쓰면 테스트 보고도 `main`이다(예: `02-main-tests.md`). 검토·검증 보고는 메인 세션이 저장해도 작성한 쪽은 그 검토자다.
  - runner 결과 폴더 안의 파일(`summary.txt` 등)은 스크립트가 정한 이름 그대로 둔다. 큰 기능의 자식 폴더 이름은 위 자식 폴더 규칙을 따른다.
- 공통 상태 파일은 두지 않는다. 폴더의 파일 목록이 곧 진행 상태다.
- 작업 폴더는 지우지 않는다. 정리는 사용자가 직접 한다(2026-10-25 사용자 결정).
- 보통의 순서와 쓰는 쪽:
  - `01-main-spec.md`(메인 세션): 작업 종류, 확인받은 입력 원문(새 기능은 명세, 버그 수정은 재현 상황, 리팩터링은 범위와 목적, 장애는 원인과 증상. 장애 수정의 작업 종류는 버그 수정이다), 사용자가 확인한 규모, 기준 커밋 SHA, backlog 항목에서 시작한 작업이면 그 항목 번호(여러 개면 모두)
  - `02-<작성한 쪽>-tests.md`(테스트를 쓴 쪽. 예: `02-test-writer-tests.md`, 중간 규모는 `02-main-tests.md`): 만든 테스트, 가정한 것, 겨냥 회귀 케이스의 sha256
  - `02-<작성한 쪽>-cases-target.json`(테스트를 쓴 쪽): 문장 피드백 LLM을 바꿀 때의 겨냥 회귀 케이스
  - `03-runner-test/`(`runner`): 테스트 커밋 시점 기록. 각 파일 첫 줄의 HEAD가 테스트 커밋이다
  - `04-main-impl.md`(메인 세션): 명세를 어떻게 해석해 무엇을 바꿨는지. `verifier`는 읽지 않는다
  - `05-runner-impl/`(`runner`): 구현 커밋 시점 기록
  - `06-main-diff-all.txt`, `06-main-diff-tests.txt`(메인 세션): `verifier`에 넘기는 변경분
  - `07-verifier-verify.md`(`verifier`)
- 중간에 생긴 사용자 결정(비용 승인, 테스트 수정 허락)이나 단계를 건너뛴 이유는, 그 시점의 다음 번호로 메인 세션이 `NN-main-decision.md`를 남긴다. 결정 파일에는 사용자 결정, 대상, 사용자에게 보인 이유만 적는다. 구현에 관한 설명은 `-impl.md`에 둔다(`verifier`가 결정 파일은 읽는다).
- `verifier`나 `instruction-reviewer`의 지적을 고치는 방법이 사용자와 정한 내용을 바꾸면, 고치기 전에 사용자에게 묻는다. 지적이 맞아도 그렇다(2026-10-25, 검토의 제안을 따라 정한 설계와 다른 공통 상태 파일을 넣었다가 되돌린 일).
  - 정한 내용: 사용자에게 확인받은 명세(이번 작업의 `01-main-spec.md` 포함), 결정 파일, 지침 검토의 `01-main-purpose.md`에 적은 정한 내용, 이번 작업 전부터 있던 지침(`.claude/CLAUDE.md`, `.claude/agents/*.md`, `.claude/skills/*/SKILL.md`)의 규칙(날짜가 없는 것 포함)
  - 바꾼다: 위의 것을 뒤집거나 다르게 바꾸는 것. 이번 작업에서 새로 넣은 줄을 고치는 것, 기존 규칙과 부딪히지 않는 줄을 더하는 것, 명세대로 코드를 고치는 것은 해당하지 않는다. 다만 새로 넣은 줄이라도 결정 파일이나 `01-main-purpose.md`의 정한 내용을 옮긴 것이면 해당한다.
  - 검토자가 붙인 표시(`verifier`의 "명세를 바꿈", `instruction-reviewer`의 [정한 내용을 바꿈])는 물어야 할 것의 최소한이다. 표시가 붙은 지적은 메인 세션이 판단을 뒤집지 않고 묻는다. 표시가 없어도 메인 세션이 보기에 정한 내용을 바꾸면 묻는다.
  - 물어서 받은 답은 다음 번호의 `NN-main-decision.md`로 남긴다.
- 구현 쪽의 설명 파일은 처음 구현이든 고친 것이든 이름을 `-impl.md`로 끝낸다(2026-10-25 사용자 결정). `verifier`가 읽지 않을 파일을 이름 하나로 가리기 위해서다. 처음 구현인지 고친 것인지는 번호와 바로 앞의 검증 보고로 안다.
- 한 번 쓴 파일은 고치지 않는다. 고친 뒤 다시 돌면 다음 번호로 이어 붙인다(예: `08-main-impl.md`, `09-runner-fix/`, `10-main-diff-all.txt`, `10-main-diff-tests.txt`, `11-verifier-verify.md`). 다시 검증할 때도 새 커밋 기준으로 변경분을 다시 만든다.
- 각자 자기 파일만 쓴다. `verifier`는 파일을 쓸 수 없으니 메인 세션이 그 보고를 그대로 저장한다.
- 다음 에이전트에는 내용을 옮겨 말하지 않고 파일 경로를 넘긴다. 명세는 `01-main-spec.md`를 넘긴다.
- 새 세션이거나 대화가 요약됐으면 `bash scripts/dev/work.sh status`로 최근 작업 폴더의 마지막 파일과 커밋하지 않은 파일을 보고(이어 할 폴더가 최근 5개에 없으면 `status --all`로 본다), 이어 할 폴더의 파일을 번호 순서로 읽고 이어서 한다. `status`는 보여 주기만 하고, 끝났는지는 메인 세션이 판단한다. 명세를 기억으로 다시 쓰지 않는다.
  - 자식 폴더 방식이면 부모 폴더의 파일을 먼저 읽고, 검증이 끝나지 않은 자식 폴더(검증 보고가 없거나, 마지막 검증 보고에 확실한 문제나 의심 가는 문제가 있는데 그 뒤 다시 검증받지 않았고 사용자가 결정 파일에서 고치지 않기로 정하지도 않은 것)를 찾아 거기서 이어서 한다. 그런 자식 폴더가 없으면, 부모의 나누는 계획에서 아직 자식 폴더가 없는 다음 항목으로 새 자식 폴더를 만든다. 계획의 항목이 모두 검증을 마쳤으면, 큰 기능 전체의 최종 보고와 backlog 정리로 넘어간다.
