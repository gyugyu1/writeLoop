# 작업 공정

## 작업 방식

`task-triage`에서 정한 작업 종류에 따라 아래 두 흐름 중 하나로 한다. 어느 쪽이든 기대 결과가 먼저다. 구현을 모르는 `qa`가 명세만 보고 구현 전에 기대 결과를 정해 커밋으로 고정하고, 구현이 끝나면 그 기대 결과로 실행해 확인한다. 만든 사람이 자기 결과를 혼자 확인하지 않게 한다(2026-10-28 사용자 결정).

### 새 기능 흐름

명세 → 시나리오(`qa`) → 구현(메인 세션) → 시나리오를 테스트로 옮겨 실행·검증(`qa`).

- 명세에 화면 동작, API, 예외 상황을 적고 사용자에게 확인받는다. 웹·모바일 양쪽 반영과 LLM 출력·비용 변화도 적는다.
- 구현 전에는 클래스·메서드 이름이 없으므로 `qa`는 시나리오와 기대 결과를 문서로 쓴다. `qa`가 시나리오를 쓰는 동안(작업 폴더에만 쓴다) 메인 세션은 구현해도 된다.
- 구현을 커밋하면 `qa`가 시나리오를 테스트 코드로 옮긴다. 기대값은 시나리오에서만 가져오고, 구현 코드는 부르는 방법을 알려고만 읽는다.
- 검증은 명세·시나리오와 결과를 비교해 빠진 것과 명세에 없는 것을 찾는다.

### 기존 코드 흐름(버그 수정, 리팩터링, 기능 변경)

테스트(`qa`) → 고치기 전 기록(`qa`) → 구현(메인 세션) → 실행·검증(`qa`).

- 고칠 코드가 이미 있으므로 `qa`가 구현 전에 테스트 코드를 쓰고, 테스트를 커밋한 뒤 지금 코드에서 돌려 고치기 전 기록을 남긴다. 그 기록이 남을 때까지 메인 세션은 저장소의 코드를 고치지 않는다.
  - 그동안 메인 세션은 저장소 밖 임시 작업 사본(`git worktree add --detach <scratchpad 아래 폴더> <기준 커밋>`)에서 구현 초안을 써도 된다(2026-11-03 사용자 결정. `qa`를 기다리는 시간을 쓰려는 것이다). 저장소와 `qa`의 실행에는 닿지 않는다. 사본에서는 커밋하지 않는다.
  - `node_modules`는 저장소의 것을 junction으로 연결한다. 사본에서는 그림 경로(`testUri`)가 달라 그림이 든 스냅샷이 실패하는데, 그 한 줄 차이뿐인지 확인하고 넘어간다. 사본에서 돌린 결과는 공식 기록이 아니다.
  - `qa` 테스트가 나오면 초안을 그 테스트에 맞춘다. 테스트를 초안에 맞추지 않는다. 초안과 테스트가 명세를 다르게 읽었으면 짐작으로 고치지 않고 사용자에게 묻는다.
  - 고치기 전 기록을 커밋한 뒤에 사본의 변경분(`git -C <사본> diff`)을 저장소에 옮겨(`git apply`) 구현 커밋을 한다. 다 쓴 사본은 junction을 먼저 지우고 `git worktree remove`로 지운다.
- 작업 종류마다 무엇을 테스트로 쓰고 고치기 전 기록에서 무엇이 나와야 하는지는 `.claude/agents/qa.md`의 "기존 코드 흐름의 테스트와 기대 결과" 표 한 곳에 둔다. 다른 지침에 같은 내용을 다시 적지 않는다.
- 명세에 적을 것: 버그 수정은 재현 상황, 리팩터링은 범위와 목적, 기능 변경은 바뀌는 동작·그대로여야 할 동작·그 때문에 고칠 기존 테스트(옛 동작을 확인하던 테스트). 사용자에게 확인받는다(기능 변경은 2026-10-31 사용자 결정).
- 고치기 전 기록이 표와 다르면 구현으로 넘어가지 않는다. 버그가 재현되지 않으면 원인을 다시 찾는다.
- 리팩터링은 구현을 작은 단계로 나눈다. 단계마다 메인 세션이 같은 테스트를 돌려 봐도 된다. 구현 중에 테스트를 고쳐서 통과시키지 않는다.
- 의존성 올리기는 리팩터링으로 다룬다. Spring Boot·Flyway·MySQL 드라이버·Hibernate를 올리면 마이그레이션 확인도 돌린다. Expo나 네이티브 모듈을 올리면 스토어 빌드가 필요하다고 보고한다.

### 두 흐름 공통

- 구현은 명세를 따른다. 메인 세션은 구현하면서 자기 테스트(단위·통합)를 함께 써도 된다. 구현 중 명세가 모호하거나 틀린 것을 찾으면 짐작해서 진행하지 않고 사용자에게 묻고, 답은 다음 번호의 `NN-main-decision.md`로 남긴다(`01-main-spec.md`는 고치지 않는다). `qa`의 시나리오나 테스트가 명세를 메인 세션과 다르게 읽었을 때도 같다.
- 큰 작업: 큰 기능은 따로 확인할 수 있는 작은 기능으로 나눠, 하나씩 위 흐름을 돈다. 나누는 방법은 명세 단계에서 사용자와 정한다.
- 명세에 없으면 검사 도구(`scripts/feedback-quality/`의 회귀 케이스와 채점 규칙, `scripts/run-feedback-quality-check.mjs`, `scripts/dev`)를 고치지 않는다. 판정 기준이나 확인 방법을 바꿔 통과시키는 일이 된다.

## 커밋 순서(중간 규모부터)

push는 CLAUDE.md의 "대화 규칙"대로 요청받았을 때만 한다.

- 기존 코드 흐름(버그 수정, 리팩터링, 기능 변경):
  1. `qa`가 쓴 테스트를 구현 전에 따로 커밋한다(`test:`).
  2. 바로 `qa`가 그 테스트(기능 변경은 고친 기존 테스트 포함)를 돌려 고치기 전 기록(`NN-runner-test/`)과 판정(`NN-qa-pretest.md`)을 남긴다. 기대 결과는 `qa.md`의 표다.
  3. 구현을 커밋한 뒤 `qa`가 실행하고 검증한다.
- 새 기능 흐름:
  1. `qa`의 시나리오 문서를 `private`에서 커밋한다. 구현 커밋보다 먼저여야 한다. 두 저장소가 따로라 `work.sh check`는 커밋 시각으로 순서를 보므로, 시나리오 커밋과 첫 구현 커밋을 한 명령에 잇달아 하지 않는다(같은 초면 순서를 정하지 못해 FAIL한다. 2026-10-31).
  2. 구현을 커밋한다. 메인 세션의 테스트는 구현과 같은 커밋이어도 된다.
  3. `qa`가 시나리오를 옮긴 테스트를 메인 세션이 따로 커밋한다(`test:`).
  4. `qa`가 실행하고 검증한다. 이 실행이 테스트 커밋 시점 기록(`NN-runner-test/`)이다.
- 메인 세션이 구현 중에 돌린 결과는 기록으로 치지 않는다. 공식 실행 기록은 늘 `qa`가 `bash scripts/dev/work.sh run`으로 남긴다(2026-10-31).
- 단위 테스트로 확인할 수 없는 변경(마이그레이션만, 운영 설정, 프롬프트 문구, 의존성 버전만)은 테스트 커밋을 건너뛴다. 대신 커밋한 뒤 `qa`가 변경 종류별 확인(마이그레이션 확인, 문법 검사, LLM 회귀, 전체 테스트)을 돌리고 검증한다. 건너뛴 이유는 결정 파일(`NN-main-decision.md`)로 남긴다.

## 에이전트(`.claude/agents/`)

메인 세션은 사용자와 대화하며 명세를 쓰고, 구현하고, 결과를 모아 커밋·backlog·보고를 한다. 하위 에이전트는 운영에 접속하지 않는다.

- 구현은 규모와 관계없이 메인 세션이 한다. 사용자와 명세를 정한 맥락을 그대로 쓰려는 것이다. 기대 결과 작성, 실행 기록, 검증은 중간 규모부터 `qa` 하나에 맡긴다(2026-10-28 사용자 결정. 그 전의 `runner`, `test-writer`를 합쳤고, 이름을 `verifier`에서 `qa`로 바꿨다).
- `qa`는 단계마다 부른다. 단계별로 하는 일은 `.claude/agents/qa.md`에 있다.
  1. 기대 결과 정하기: 명세를 사용자에게 확인받은 뒤
  2. 테스트 커밋 시점 실행(고치기 전 기록): 기존 코드 흐름의 테스트를 커밋한 뒤
  3. 시나리오를 테스트로 옮기기: 새 기능의 구현을 커밋한 뒤
  4. 실행과 검증: 구현(새 기능은 3단계 테스트까지)을 커밋한 뒤, 고친 뒤에도 다시
- 4단계는 처음 검증이든 고친 뒤 다시 검증이든 앞 단계의 `qa`를 이어 쓰지 않고 늘 새 `qa`로 부른다. 1~3단계는 같은 `qa`를 이어 써도 된다(2026-10-31 사용자 결정. 두 작업 시범에서 새 `qa`가 맥락은 절반 남짓이면서 결정 파일만 읽고 앞 단계를 이어받았고, 헛짚음 없이 실제로 고칠 만한 문제를 찾았다).
- 고친 뒤 다시 검증은 고친 것이 작으면 가볍게 한다(2026-11-12 사용자 결정. 한 줄을 고쳐도 새 `qa`가 전체를 다시 읽고 다 돌려 테스트가 구현보다 오래 걸렸다).
  - 가볍게 하는 조건(메인 세션이 판단한다): 앞 검증 보고 뒤의 커밋이 그 보고의 지적을 고친 것뿐이고, 마이그레이션·운영 설정·LLM 프롬프트·스키마·모델·API 요청·응답 모양·의존성을 바꾸지 않았고, 바꾼 줄이 적다(대략 50줄 이하).
  - 이때도 새 `qa`로 부르되 "가벼운 다시 검증"이라고 넘긴다. `qa`가 하는 일은 `.claude/agents/qa.md`의 4단계 "가벼운 다시 검증"에 있다(바뀐 영역 확인만 돌리고, 고친 변경분과 앞 지적만 본다).
  - 조건에 맞지 않거나, 가벼운 다시 검증이 새 문제를 찾으면 지금처럼 전체를 다시 검증한다. push 전 CI는 늘 전체를 돈다.
- 부를 때는 작업 폴더 경로와 단계만 넘긴다. 파일을 하나씩 고르거나 내용을 옮겨 말하지 않는다. 메인 세션이 고르다 빠뜨리는 파일이 없게 하려는 것이다. LLM 회귀가 들어가면 사용자 승인과 요청 수도 넘긴다.
- 1단계(기대 결과 정하기)와 3단계(시나리오를 테스트로 옮기기)는 바뀌는 영역이 둘 이상이면(예: 웹과 모바일, 백엔드와 화면) 영역마다 `qa`를 하나씩 동시에 부를 수 있다(2026-11-03 사용자 결정. 웹·모바일을 한 `qa`가 차례로 맡으면 오래 걸렸다).
  - 부를 때 작업 폴더 경로와 단계에 더해, 맡을 영역과 보고 파일 번호를 넘긴다. 번호는 메인 세션이 `work.sh next`로 보고 영역마다 겹치지 않게 미리 나눠 준다(예: 웹 `04-qa-tests.md`, 모바일 `05-qa-tests.md`).
  - 각 `qa`는 자기 영역의 테스트 파일과 자기 보고 파일만 쓴다. 명세가 모호하거나 영역 사이에 걸치는 판단은 각자 보고에 적고, 메인 세션이 모아 사용자에게 묻는다.
  - 2단계(고치기 전 기록)와 4단계(실행과 검증)는 지금처럼 `qa` 하나로 한다. `work.sh run`이 같은 저장소에서 테스트를 돌리고 기록 폴더를 만들어, 동시에 돌면 기록이 섞이거나 빌드 폴더가 잠긴다.
- `qa`가 쓴 파일(보고, 시나리오, 겨냥 케이스, 실행 기록의 `summary.txt`, 테스트)은 그 단계가 끝나면 메인 세션이 커밋한다(`work-folder`).
- `qa`가 실행하는 동안에는 저장소 파일을 고치지 않고 끝날 때까지 기다린다. 새 기능의 시나리오를 쓰는 동안(작업 폴더에만 쓴다)은 구현해도 된다.
- 실행은 `qa`가 `work.sh run`으로 한다. 돌릴 확인은 도구가 기준 커밋부터 바뀐 경로로 고른다(바뀐 영역만. 마이그레이션 확인, 모바일 lint, 워크플로·운영 스크립트 문법처럼 CI에도 있는 확인도 해당하면 push 전에 돌린다). 사용법은 `qa.md`의 "실행과 기록"에 있다.
  - 도구가 돌리지 않는 확인: LLM 회귀는 사용자 승인과 요청 수를 받아 `qa`에 넘길 때만 돈다(`--llm-approved`). nginx 문법은 필요하면 메인 세션이 명령을 넘긴다. 도구가 `NEEDS`로 알린 확인은 메인 세션이 판단해 사용자에게 묻거나 넘긴다.
  - 환경 문제(Docker를 켜지 못함, 포트 사용 중, 빌드 폴더 잠금)로 실행하지 못하면, 메인 세션이 원인을 사용자에게 알리고 해결한 뒤 다시 맡긴다. 실행하지 못한 확인을 통과로 보고하지 않는다.
- 4단계에서 `qa`가 실행 기록(`work.sh run`), 변경분(`work.sh diff`), 기록 대조(`work.sh check`)를 만들고 판정한다. 세부와 판정 기준은 `.claude/agents/qa.md`에 있다. 메인 세션은 구현 설명을 `-impl.md`로 남기고, `qa`는 그 파일을 읽지 않는다.
- `instruction-reviewer`: 사용자가 요청할 때만 작업 지침 변경을 검토한다(`instruction-change` 스킬의 `review.md`). 읽기만 하고, 문제와 더 나은 방안을 보고한다.
- 메인 세션은 `qa`의 테스트(백엔드는 이름이 `SpecTest`로 끝나는 클래스, 채점 규칙은 이름이 `[spec]`으로 시작하는 테스트, 검사 스크립트는 이름이 `.spec.test.sh`로 끝나는 파일, 웹은 이름이 `.spec.test.ts(x)`로 끝나는 파일)를 고치지 않는다.
  - 예외: 구현 때문에 바뀐 클래스·메서드 이름, import, 패키지 경로를 따라가는 수정은 메인 세션이 구현 커밋에서 한다. `qa`의 테스트와 이번 작업 전부터 있던 테스트 모두 그렇다. 단언, 기대값, 테스트 입력과 준비 데이터는 건드리지 않고, `qa`가 4단계에서 그 변경이 이름·경로 따라가기뿐인지 본다(2026-10-31 사용자 결정). 리팩터링에서 이름을 바꿀 때마다 결정을 받는 수고를 줄이려는 것이다.
- 검증에서 나온 문제를 고치면, 고친 것을 커밋하고 `qa`에 다시 실행과 검증을 맡긴다.
- `qa`의 지적에 동의하지 않으면 혼자 넘기지 않는다. 근거(코드 위치, 실행 기록)를 붙여 사용자에게 보고하고 결정받는다. `qa`의 테스트가 실패했는데 메인 세션이 보기에 테스트(명세 해석)가 틀렸을 때도 같다. 코드를 테스트에 억지로 맞추지 않는다.
- 같은 문제로 고침과 검증을 두 번 돌아도 풀리지 않으면 멈추고, 시도한 것과 남은 문제를 사용자에게 보고한다.
- 테스트 수정(위의 이름·경로 따라가기는 빼고)은 사용자가 결정한다. 대상은 `qa`의 테스트와 이번 작업 전부터 있던 테스트다. 메인 세션이 이번 작업에서 새로 쓴 테스트는 메인 세션이 고쳐도 된다. 결정하면 결정 파일(`NN-main-decision.md`)로 남기고, `qa`의 테스트는 `qa`가 고친다. `test:` 커밋으로 따로 남긴다. 결정 파일은 작업 폴더에 있으므로 `qa`가 읽는다.
  - 구현 뒤에 `qa`의 테스트를 더하기로 하면(새 기능의 3단계는 빼고, 실행 기록 이름은 `test-add`), 결정 파일에 더하는 테스트마다 이미 있는 동작을 지키는 것(테스트 커밋 시점에 통과가 맞음)인지, 새 동작이나 버그를 겨냥한 것(실패가 맞음)인지 적는다.

## 변경 종류별로 더 할 것

- DB 스키마 변경은 크기와 관계없이 `qa`의 마이그레이션 확인과 검증을 둔다. 운영 설정 변경도 크기와 관계없이 검증을 따로 둔다(2026-10-24 V110 사고).
- 문장 피드백 LLM(프롬프트·스키마·모델·미션 선택)을 바꾸면 6건 회귀(`scripts/dev/run-llm-smoke.sh`)를 돌린다.
  - 이번 변경을 겨냥한 회귀 케이스를 구현 전에 `qa`가 작업 폴더에 `NN-qa-cases-target.json`으로 10건 이하로 쓰고(1단계), 메인 세션이 구현 커밋 전에 `private`에서 커밋한다. 형식은 `scripts/feedback-quality/cases.smoke.json`과 같다. 쓴 직후 파일의 sha256 전체를 그 단계의 보고에 적고, 메인 세션이 사용자에게도 대화로 알린다. 구현 뒤에 케이스를 고쳐 통과시키지 못하게 하려는 것이다.
  - 메인 세션이 요청 수(`--dry-run`, 케이스 파일을 모두 합친 수)를 사용자에게 알리고 승인받은 뒤, `qa`가 겨냥 케이스와 6건 세트를 함께 돌린다.
  - `qa`는 원본 리포트와 피드백 원문(`feedback-diagnosis-logs.tsv`)을 보고, 6건 세트의 알려진 실패 유형 셋(`qa.md`)은 따로 표시한다. 최종 보고에는 실제 응답 몇 개를 붙여 사용자도 보게 한다.
- 코치, 영어일기, Now in English의 LLM을 바꾸면, 아직 회귀 세트도 키를 넣어 부를 스크립트도 없다(일기 평가셋은 backlog). 사용자가 개발 앱에서 직접 불러 보고 판단한다. 최종 보고에 확인할 화면과 입력 예를 "사용자가 직접 볼 것"으로 적는다.
- `application*.yml`이 바뀌면 `qa`의 실행에 마이그레이션 확인(`check-db-migrations.sh`, 빈 DB·기존 DB로 백엔드 기동)이 들어간다. 빈 구성(설정 클래스, 생성자 의존성)만 바뀌면 백엔드 테스트의 통합 테스트가 앱 전체를 실제 DB로 띄우는 것으로 기동을 확인한다. CI도 둘 다 돌리지만 push 뒤에야 돌고, 실패하면 배포가 막힌다.
- 웹 화면 변경은 `qa`가 화면 테스트(Vitest, Testing Library)를, 모바일 화면 변경은 화면 테스트(Jest·jest-expo, React Native Testing Library)를 쓴다. 어느 쪽이든 테스트로 볼 수 없는 것(모양, 애니메이션, 실제 기기)은 명세에 확인 목록(화면, 조작, 기대 결과)을 적는다.
  - 최종 보고에 이 목록과 `qa`의 "사용자가 직접 볼 것", 의심·미확인 항목을 "사용자가 직접 볼 것"으로 넘긴다.
  - 화면 버그는 재현 절차를 적는다. 재현 테스트를 못 쓰면 그 이유를 보고한다.
- 운영 설정 변경은 `qa`가 문법을 확인한다: compose는 `docker compose config -q`, 워크플로는 actionlint 컨테이너, `scripts/ops/*.sh`는 `bash -n`, nginx는 가능하면 `nginx -t`.
  - `deploy.yml`을 바꾸면, 보고에 서버에서 `scripts/ops/deploy.sh`를 직접 돌리는 비상 롤백 방법을 적는다. 이 파일이 깨지면 Actions의 롤백도 같이 깨진다.
- Claude 설정(`.claude/hooks`, `.claude/settings.json`)을 바꾸면 `qa`가 훅의 파이썬 문법(`ast.parse`, 캐시 파일을 남기지 않는다)과 JSON 문법을 확인한다. `.claude/**`만 바뀐 push는 CI가 돌지 않는다.
- 로컬 API 호출(`check-db-migrations.sh --api`)은 로그인 없는 API만 부를 수 있다. 로그인이 필요한 API는 백엔드 단위 테스트로 확인한다.
