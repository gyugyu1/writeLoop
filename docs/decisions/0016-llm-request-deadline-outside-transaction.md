# LLM 호출은 요청 단위 마감 안에서, DB 트랜잭션 밖에서 한다

## Context and Problem Statement

LLM을 부르는 기능의 서버 시간 제한이 앱 시간 제한보다 길었다.

| 기능 | 서버(이전) | 앱 |
|---|---|---|
| 문장 피드백 | 호출당 40초. 첫 호출, 시간 초과 재시도, 계약 위반 재시도가 겹치면 최악 약 120초 | 90초 |
| 코치 | 호출당 120초. 슬롯 번역과 다운그레이드 재시도까지 여러 번 부를 수 있다 | 45초 |
| Now in English 코치·회고 | 120초 | 45초 |
| 영어일기 | 120초(운영은 `.env`로 75초) | 90초 |

앱이 먼저 포기하면 서버가 준비한 대체 응답이나 오류 안내는 아무도 보지 못하고, 서버는 계속 기다리며 비용을 쓴다. nginx도 120초까지 기다렸다.

또 문장 피드백은 요청 전체가 하나의 DB 트랜잭션이었다. 그래서 LLM을 기다리는 동안(보통 13초, 최악 80초 이상) DB 연결을 붙잡았다. 연결 풀은 기본 10개라, 피드백 요청이 몰리면 로그인·홈·기록 같은 다른 요청까지 연결을 기다리다 실패할 수 있었다.

## Decision Drivers

* 서버가 앱보다 먼저 끝내야 대체 응답과 오류 안내가 사용자에게 닿는다.
* 재시도는 남은 시간이 있을 때만 의미가 있다.
* 느린 LLM 호출이 DB 연결을 다 써서 다른 기능을 막으면 안 된다.
* LLM이 실패해도 빈 세션 같은 부분 저장이 남으면 안 된다.

## Considered Options

* 호출마다 시간 제한만 줄인다.
* 요청 단위 마감을 두고, 모든 호출이 남은 시간 안에서 나눠 쓴다.
* LLM 호출을 비동기 작업으로 바꾸고 앱이 결과를 기다려 조회한다.

## Decision Outcome

Chosen option: "요청 단위 마감", because 호출 수가 기능마다 다르고 상황에 따라 달라서(재시도, 슬롯 번역 수), 호출마다의 제한만으로는 최악의 경우를 막을 수 없기 때문이다. 비동기 작업은 효과가 크지만 앱과 서버를 모두 바꿔야 해서 지금 규모에는 과하다.

* `LlmRequestDeadline`
  * 서비스가 요청을 시작할 때 `within(예산, 작업)`으로 마감을 연다.
  * OpenAI 호출은 모두 `OpenAiStructuredOutputSupport.buildResponsesRequest`를 지나간다. 여기서 "호출마다의 제한"과 "남은 시간" 중 짧은 쪽만 기다린다.
  * 남은 시간이 5초보다 적으면 호출하지 않고 예외를 던진다. 각 기능은 기존 실패 처리(대체 응답 또는 오류)로 넘어간다.
* 기능별 값(`application.yml`):

  | 기능 | 호출당 제한 | 요청 마감 |
  |---|---|---|
  | 문장 피드백 | 40초 | 80초 |
  | 코치 | 40초 | 40초 |
  | Now in English 코치·회고 | 40초 | 호출 한 번 |
  | 영어일기 | 75초 | 호출 한 번 |

* nginx `proxy_read_timeout`은 85초로 줄인다. 앱(90초)보다 짧고 서버 마감(80초)보다 길다.
* 문장 피드백(`FeedbackService.review`)은 트랜잭션을 셋으로 나눈다.
  1. 준비(짧은 트랜잭션): 검증, 세션 확인, 같은 제출 확인, 시도 번호
  2. LLM 호출(트랜잭션 밖)
  3. 저장(짧은 트랜잭션): 세션과 답변 저장. 기다리는 동안 같은 제출이 먼저 저장됐으면 그 결과를 돌려준다.
  * 새 세션은 3에서 만든다. LLM이 실패해도 빈 세션이 남지 않는다.
  * 진단 로그는 3이 끝난 뒤 따로 저장한다. 로그 저장이 실패해도 답변은 남는다.

### Consequences

* Good, because 모든 LLM 기능이 앱 제한 안에서 결과, 대체 응답, 오류 중 하나를 돌려준다.
* Good, because 마감이 가까우면 재시도하지 않아 쓸모없는 호출 비용이 줄어든다.
* Good, because 문장 피드백이 LLM을 기다리는 동안 DB 연결을 쓰지 않는다.
* Bad, because 마감이 ThreadLocal이라, LLM 호출을 다른 스레드로 넘기면 마감이 따라가지 않는다. 그렇게 바꿀 때는 마감도 함께 넘겨야 한다.
* Bad, because Gemini 클라이언트는 마감을 따르지 않는다. 운영은 OpenAI만 쓴다(ADR-0005). Gemini로 바꾸면 같은 처리를 넣어야 한다.
* Bad, because 준비와 저장 사이가 트랜잭션으로 묶이지 않는다. 같은 세션에 서로 다른 제출이 동시에 오면 같은 시도 번호가 날 수 있다. 이전에도 같은 위험이 있었고, 시도 번호 충돌은 별도 과제다.

### Confirmation

* `LlmRequestDeadlineTest`: 남은 시간 계산, 최소 시도 시간, 중첩 마감
* `OpenAiFeedbackClientTest.skipsTheTimeoutRetryWhenTheRequestDeadlineIsTooClose`
* `FeedbackServiceTest`
  * LLM 호출이 트랜잭션 밖인지
  * LLM 실패 때 새 세션을 만들지 않는지
  * 새 세션이 첫 답변보다 먼저 저장되는지
  * 기다리는 동안 같은 제출이 저장된 경우

## More Information

* ADR-0008(호출당 40초, 시간 초과 1회 재시도)은 그대로다. 이 결정은 그 재시도들이 쓸 수 있는 전체 시간을 정한다.
* 새 LLM 기능을 만들 때는 서비스 입구에서 `LlmRequestDeadline.within`으로 마감을 열고, DB 트랜잭션 밖에서 LLM을 부른다.
