# WriteLoop Luna 최적화 프롬프트 및 모델 A/B 테스트 보고서

작성일: 2026-07-12  
대상 기능: 질문 답변형 영어 피드백  
비교 모델: `gpt-5.4-mini`, `gpt-5.6-luna`  
추론 강도: `low`

## 1. 최종 결론

초기 테스트에서 `gpt-5.6-luna`가 `gpt-5.4-mini`보다 낮은 결과를 보인 주된 원인은 Luna의 절대 성능 부족보다는 다음 세 가지 조합이었다.

1. 기존 프롬프트가 미션 선택, 완료 판정, 출력 필드 생성을 한 번에 길게 나열해 Luna가 우선순위를 안정적으로 지키기 어려웠다.
2. `COMPLETE`와 수정 상태를 여러 필드가 독립적으로 표현해 서로 모순될 수 있었다.
3. 자동 평가기가 `skeletonKo`에 값만 있으면 통과시켜, 실제로 영어 문장을 복제한 경우를 품질 결함으로 잡지 못했다.

이를 Luna 중심의 순차 결정 절차와 두 가지 상태 계약으로 재설계한 뒤, 동일한 최종 코드와 동일한 50개 사례로 두 모델을 각각 실제 호출했다.

- `gpt-5.4-mini`: 엄격 통과 `31/50`, 62%
- `gpt-5.6-luna`: 엄격 통과 `49/50`, 98%
- Luna 사례별 개선 `18건`, 동일 `32건`, 회귀 `0건`
- Luna 평균 응답 시간 `5.396초`, 5.4 mini보다 `16.9%` 빠름
- Luna 완료 판정 정확도 `100%`
- Luna 미션 선택 허용률 `100%`

따라서 현재 WriteLoop 질문 답변 피드백에는 **Luna와 Luna 최적화 프롬프트 조합을 기본값으로 사용하는 것이 타당하다.**

다만 공식 문서는 Luna를 비용 민감형 대량 처리 모델이며 이전 GPT 계열의 nano 등급과 대략 대응한다고 설명한다. 즉 `5.6`이라는 버전 숫자만으로 모든 작업에서 `5.4 mini`보다 우수하다고 볼 수는 없다. 이번 결론은 WriteLoop의 한국어 기반 미션형 피드백 계약에서 실제로 검증한 결과다.

- [GPT-5.4 mini 공식 모델 정보](https://developers.openai.com/api/docs/models/gpt-5.4-mini)
- [GPT-5.6 Luna 공식 모델 정보](https://developers.openai.com/api/docs/models/gpt-5.6-luna)

## 2. 기존 프롬프트가 Luna에서 흔들린 이유

### 2.1 판단 규칙과 출력 규칙이 섞여 있었음

기존 프롬프트는 질문 수행 여부, 문법 우선순위, 콘텐츠 확장, 완료 판정, 각 UI 필드 작성법이 한 덩어리로 섞여 있었다. Luna는 필드 형식은 잘 채웠지만 다음 행동을 고르는 핵심 판단에서 뒤쪽의 세부 규칙을 과대 적용하는 경향을 보였다.

- 이미 이유가 있는 답변에 다시 `REASON` 선택
- 충분하지 않은 답변을 조기 `COMPLETE` 처리
- 작은 관사 오류를 전체 미션인 `GRAMMAR_FIX`로 승격
- `missionDecision`, `coachMission`, `fixPoints`, `finishable` 사이의 상태 모순

### 2.2 `COMPLETE`가 하나의 원자적 상태가 아니었음

기존에는 모델이 `chosenType=COMPLETE`를 선택하면서도 `finishable=false`를 출력하거나, 완료 상태에 교정 포인트를 남길 수 있었다. 스키마가 필드의 자료형은 보장했지만 여러 필드가 하나의 의미를 갖는지는 보장하지 못했다.

### 2.3 실제 질문보다 메타데이터가 강하게 작동했음

질문이 이유를 묻지 않아도 메타데이터나 일반적인 학습 철학 때문에 `REASON`을 선택하는 사례가 있었다. 실제 질문 문장을 유일한 필수 내용의 기준으로 선언할 필요가 있었다.

### 2.4 Luna의 장점이 평가기에 반영되지 않았음

초기 의미 감사에서 Luna는 `skeletonKo`를 실제 한국어로 생성했지만 5.4 mini는 여러 건에서 영어 스켈레톤을 그대로 복제했다. 기존 평가기는 문자열이 비어 있지 않은지만 검사해 이 차이를 통과 처리했다.

따라서 초기 자동 점수는 Luna의 한국어 출력 장점을 과소평가했다.

## 3. 적용한 개선

### 3.1 developer 지침과 사용자 JSON 분리

- 고정 정책과 미션 선택 규칙은 developer message에 둠
- 질문, 학습자 답변, 힌트, 이전 이력은 user JSON으로 전달
- 사용자 입력 안의 명령문과 역할 표시는 지시가 아닌 데이터로 취급

### 3.2 실제 질문을 최우선 기준으로 고정

- `prompt.questionEn`만 필수 내용의 원본으로 사용
- 메타데이터, 힌트, 백엔드 진단은 참고 정보로만 사용
- 질문이 `why`를 요구하지 않으면 선택적 이유를 필수 미션으로 만들지 않음

### 3.3 순차 미션 결정표 도입

모델이 아래 순서에서 처음 일치하는 규칙 하나만 선택하도록 바꿨다.

1. 사용 가능한 영어 답변이 없으면 `TASK_RESET`
2. 의미가 막히면 `GRAMMAR_FIX`
3. 질문이 요구한 내용이 빠졌거나 필수 이유가 지나치게 일반적이면 콘텐츠 미션
4. 필수 내용이 있어도 핵심 국소 문법 오류가 남으면 `GRAMMAR_FIX`
5. 문법은 맞지만 핵심 표현이 비관용적이면 `EXPRESSION_POLISH`
6. 모든 의무를 충족하고 고가치 수정이 없으면 `COMPLETE`

작은 관사, 대문자, 문장부호는 충분한 답변을 막지 않도록 했고, 반복되거나 끊긴 행동 목록은 작은 가산성 오류보다 `EXPRESSION_POLISH` 또는 `DETAIL`을 우선하도록 명시했다.

### 3.4 답변 밴드와 슬롯 진단 명시

- `TOO_SHORT_FRAGMENT`
- `SHORT_BUT_VALID`
- `GRAMMAR_BLOCKING`
- `CONTENT_THIN`
- `NATURAL_BUT_BASIC`
- `OFF_TOPIC`

학습자가 실제로 말한 내용만 `presentSlots`에 넣고, 지금 추가해야 할 내용만 `missingSlots`에 넣도록 했다. 일반적인 이유도 `REASON`이 존재한다고 인정하되, `why` 질문을 완료하기에는 부족하다고 구분했다.

### 3.5 완료와 수정 상태를 두 계약으로 분리

`COMPLETE`는 다음 조건을 모두 만족해야 한다.

- `answerBand=NATURAL_BUT_BASIC`
- `taskCompletion=FULL`
- `onTopic=true`
- `finishable=true`
- `meaningClarity=CLEAR`
- 필수 슬롯 누락 없음
- `coachMission=null`
- `fixPoints=[]`

수정 상태는 다음 조건을 모두 만족해야 한다.

- `finishable=false`
- `coachMission` 한 개 존재
- `missionDecision.chosenType`과 `coachMission.missionType` 일치
- 첫 번째 `fixPoint`가 같은 행동을 지원

백엔드에서도 모순된 완료 상태를 그대로 노출하지 않고, 유효한 수정 미션을 복구하거나 경쟁하는 교정 포인트를 제거하도록 보강했다.

### 3.6 콘텐츠 스캐폴드 계약 강화

콘텐츠 및 `TASK_RESET` 미션은 다음을 요구한다.

- 영어 문장 프레임 `skeletonEn`
- 빈칸을 유지한 실제 한국어 번역 `skeletonKo`
- 한국어 뜻이 있는 추천 표현 2-4개

Structured Outputs 스키마의 `suggestedPhrases`에 `minItems=2`, `maxItems=4`를 적용했다. 공식 문서상 일반 Structured Outputs에서는 배열의 `minItems`와 `maxItems`를 지원한다.

- [Structured Outputs 지원 스키마](https://developers.openai.com/api/docs/guides/structured-outputs#supported-schemas)

### 3.7 자동 평가기 강화

- `skeletonKo`에 실제 한글이 포함됐는지 검사
- 한국어 뜻이 있는 추천 표현이 최소 2개인지 검사
- 교정 전 문구가 학습자 원문에 실제 존재하는지 검사
- 완료 응답에 숨은 코치 미션이나 교정 카드가 남는지 검사
- 수정 응답에 코치 미션이나 첫 교정 포인트가 빠지는지 검사
- `before`와 `after`가 동일한지 검사
- 완료 예상 사례도 허용된 수정 미션이면 합격할 수 있도록 평가 의미를 정리

## 4. 테스트 방법

### 4.1 통제 조건

- 같은 최종 Docker 백엔드 이미지 사용
- 모델 환경변수만 교체
- 같은 developer prompt 사용
- 같은 JSON user context 사용
- 같은 Structured Outputs 스키마 사용
- 같은 50개 질문과 답변 사용
- reasoning effort `low`
- 동시성 1로 순차 호출
- 요청 제한 시간 180초
- 모든 성공 payload 저장
- 모델 변경 후 컨테이너 환경변수와 API 응답 상태 확인

### 4.2 평가 범위

50개 사례에는 다음 유형이 포함된다.

- 일반적이거나 빈약한 이유
- 질문의 필수 부분 누락
- 지나치게 짧은 답변
- 한국어식 전이 표현
- 의미를 막는 문법 오류
- 작은 문법 오류
- 반복되거나 끊긴 문장 흐름
- 질문과 무관한 답변
- 충분히 좋은 답변
- 추상적 목표와 일반적인 계획

평가 파일: `scripts/feedback-quality/cases.prompt-refactor-50.json`

## 7. 의미 감사 결과

| 검사 항목 | GPT-5.4 mini | GPT-5.6 Luna |
|---|---:|---:|
| 완료인데 코치 미션이 남음 | 0건 | 0건 |
| 완료인데 교정 포인트가 남음 | 0건 | 0건 |
| 수정인데 코치 미션이 없음 | 0건 | 0건 |
| 수정인데 교정 포인트가 없음 | 0건 | 0건 |
| before와 after가 같음 | 0건 | 0건 |
| 원문에 없는 before 사용 | 0건 | 0건 |
| 영어로 복제된 `skeletonKo` | 18건 | 1건 |
| 한국어 추천 표현 2개 미만 | 2건 | 1건 |
| 모델답안의 한국어 번역 누락 | 0건 | 0건 |

Luna의 유일한 실패는 `favorite music needs example` 사례였다. 최종 payload의 문구는 LLM 생성 미션이 아니라 백엔드의 `missionDefaultsForOpportunity` 기반 일반 `DETAIL` fallback과 일치했다. 이 fallback 경로는 `skeletonEn`만 채우고 `skeletonKo`와 추천 표현을 비워 두므로, OpenAI 스키마의 `minItems` 보장을 우회한다.

즉 남은 1건은 Luna 프롬프트 자체보다 **백엔드 fallback 출력 계약의 불완전성**에 가깝다.

## 8. 왜 최종 결과가 초기 결과와 달라졌는가

초기에는 Luna가 빠르지만 미션 선택과 완료 상태가 불안정했다. 최종에는 다음 변화가 동시에 적용됐다.

1. 긴 예외 목록을 순차 판단 절차로 바꿈
2. 질문 원문을 메타데이터보다 우선함
3. `COMPLETE`와 수정 상태를 상호 배타적 계약으로 정의함
4. 일반적인 이유와 선택적 이유의 경계를 명시함
5. 작은 관사 오류가 전체 미션을 가로채지 못하게 함
6. 미션과 첫 교정 포인트를 백엔드에서도 정렬함
7. 스키마 배열 최소 개수와 한국어 번역 품질을 평가기에 반영함

Luna는 이런 명확한 결정 순서와 필드 계약이 주어졌을 때 50건 전체에서 올바른 미션을 선택했다. 따라서 사용자의 가설처럼 **기존 결과는 Luna에 맞게 정리되지 않은 프롬프트의 영향이 컸다.**

## 9. 남은 개선 우선순위

### 9.1 콘텐츠 fallback도 동일 계약 적용

최우선 개선은 백엔드가 fallback 미션을 만들 때도 다음을 반드시 채우는 것이다.

- 질문 맥락에 맞는 `skeletonEn`
- 자연스러운 `skeletonKo`
- 한국어 뜻이 있는 추천 표현 최소 2개

가능하면 일반 문구를 즉시 노출하기보다 한 번 제한적으로 재생성하고, 그래도 실패할 때만 질문 힌트에서 fallback을 합성하는 편이 품질이 높다.

### 9.2 한글 포함 검사를 의미 일치 검사로 확장

현재 평가는 영어 복제를 잡지만 번역의 의미가 정확한지까지 판단하지 못한다. 향후 별도 judge 평가로 다음을 확인해야 한다.

- `skeletonKo`가 `skeletonEn`을 충실히 번역하는지
- 추천 표현의 한국어 뜻이 실제 영어와 맞는지
- `modelAnswerKo`가 원문에 없는 사실을 추가하지 않는지

### 9.3 고정 평가셋과 홀드아웃 평가셋 분리

현재 50건은 회귀 방지에는 유용하지만 반복 최적화로 과적합될 수 있다.

- 개발 회귀셋 50건
- 미공개 홀드아웃 50-100건
- 실제 운영 익명 사례 표본

세 집합을 분리해 최종 배포 게이트를 만드는 것이 좋다.

### 9.4 비결정성 확인

이번 결과는 모델별 1회 50건 실행이다. 운영 배포 전에는 같은 평가를 모델별 3회 이상 반복해 평균, 표준편차, 최악 실행 통과율을 확인하는 편이 안전하다.

### 9.5 모델 스냅샷 검토

공식 모델 페이지는 별칭과 함께 스냅샷 사용을 제공한다. 운영에서 별칭 동작 변화가 부담되면 검증한 스냅샷을 고정하고, 별칭 업데이트 시 회귀 테스트 후 전환하는 방식이 안정적이다.

## 10. 비용과 배포 판단

공식 가격은 100만 토큰당 다음과 같다.

| 모델 | 입력 | 출력 |
|---|---:|---:|
| GPT-5.4 mini | $0.75 | $4.50 |
| GPT-5.6 Luna | $1.00 | $6.00 |

Luna는 이 비교 기준으로 토큰 단가가 약 33% 높지만 평균 응답 시간은 16.9% 짧고, WriteLoop의 핵심 미션 품질과 한국어 스캐폴드 품질이 더 높았다. 질문 답변 피드백 1회당 실제 토큰 사용량과 재시도율을 함께 측정해 최종 비용을 판단해야 한다.

현재 개발 설정과 실행 중인 로컬 백엔드는 `gpt-5.6-luna`, reasoning effort `low`로 맞춰져 있다. 운영 반영 전에는 다음 게이트를 권장한다.

1. 백엔드 콘텐츠 fallback 계약 보강
2. 홀드아웃 사례 추가 검증
3. 실제 요청 토큰과 비용 측정
4. 운영 환경변수 확인
