- 실행일: 2026-07-13
- 대상: 질문 답변 피드백 API `/api/feedback`
- 실제 모델: `gpt-5.6-luna`
- reasoning effort: `low`
- 호출 방식: 실제 OpenAI API 100회, 동시성 2
- 질문 구성: 20개 질문 유형 × 답변 단계 5개

## 3. 핵심 발견

### A. 질문 메타데이터 분류가 일부 질문의 실제 요구를 놓친다

`prompt-balance-1102`는 “Explain both sides and give your opinion.”이라고 묻지만 DB에는 `OPINION`만 필수로 저장됐다. 그 결과 장점만 쓴 답변도 완료 처리됐다. `prompt-problem-1108`은 “explain what you do about it”이라고 해결 행동을 요구하지만 `PROBLEM`만 필수이고 `SOLUTION`은 선택으로 남아, 문제만 적은 답변이 완료됐다.

원인은 `086`의 정규식이 `both sides`, `what you do about it` 같은 실제 문구를 포괄하지 못하기 때문이다. 슬롯 체계는 통합됐지만 질문을 슬롯으로 변환하는 규칙의 커버리지가 아직 충분하지 않다.

### B. 백엔드는 슬롯 증거의 문자열 포함 여부만 검증한다

백엔드는 LLM이 제출한 `slotEvidence`가 학습자 답변의 실제 부분 문자열인지, 같은 증거를 중복 사용하지 않았는지는 검증한다. 하지만 그 문자열이 정말 해당 슬롯의 의미인지까지는 검증하지 않는다.

예를 들어 `My favorite place near my home is the riverside park.`는 `CHOICE` 외 보강 내용이 충분하지 않은데도 완료됐다. LLM이 답변 일부를 선택 보강 슬롯으로 잘못 분류하면 `minimumDepthSlots=1`을 형식상 충족할 수 있기 때문이다. 현재 구조는 “증거가 답변에 존재한다”는 것은 보장하지만 “증거의 의미가 슬롯과 맞는다”는 것은 보장하지 못한다.

### C. canonical 슬롯이 제한된 UI 미션으로 변환될 때 의미가 약해진다

DB와 LLM은 `DISADVANTAGE`, `NOW_STATE`, `PLAN`, `SOLUTION`처럼 구체적인 슬롯을 사용하지만, 화면의 `focusType`은 `DETAIL`, `SITUATION`, `REASON` 등 더 적은 분류만 사용한다. 변환 과정에서 다음과 같은 문제가 발생했다.

- 단점을 추가해야 하는 답변에 “언제, 어디서, 어떤 상황인지 붙여 보세요”가 표시됨
- 현재 생각을 추가해야 하는 회고 답변에 일반적인 `SITUATION` 또는 `REASON` 미션이 표시됨
- 모델 답안은 올바르게 단점이나 현재 상태를 추가했지만, 제목·설명·스캐폴드는 다른 행동을 안내함

즉, 내부 슬롯 선택은 맞아도 사용자에게 보이는 피드백이 슬롯의 의미를 정확히 전달하지 못한다.

### D. 내용 미션의 스캐폴드 계약이 14건에서 깨졌다

내용 보강 미션은 `skeletonEn`, 한국어 `skeletonKo`, 한국어 뜻이 있는 표현 선택지 2개 이상이 필요하다. 14건에서 영어 골격만 있거나 표현이 1개뿐이었다. 특히 막연한 이유를 구체화하는 `DETAIL`, 회고의 상태 추가, `TASK_RESET`에서 반복됐다.

예: `My favorite color is blue because it is nice.`에 구체화 방향은 맞았지만, `I usually do this when ____.`이라는 질문과 맞지 않는 공통 스캐폴드가 사용됐고 한국어 골격과 표현 선택지도 부족했다.

### E. 내용 추가를 문법 수정으로 위장하는 사례가 있다

`After grocery shopping, I go home and put the food away.`는 문법적으로 자연스럽다. 그러나 모델은 뒤에 이유를 추가한 문장을 만들고 이를 `GRAMMAR_FIX`로 분류했다. 이는 문법 진단과 내용 미션의 경계가 아직 완전히 분리되지 않았음을 보여준다. `before I become late`처럼 실제로 어색한 표현을 고친 사례와 구별되어야 한다.

## 4. 잘 동작한 부분

- 명백한 문법 오류 11건은 모두 `GRAMMAR_FIX`로 정확히 처리했다.
- 오프토픽 20건 중 19건은 방향 자체를 `TASK_RESET`으로 인식했다.
- 완성 답변 20건 중 19건은 완료 또는 허용 가능한 선택적 다듬기로 처리했다.
- 필수 슬롯이 DB에 정확히 저장된 질문에서는 `REASON`, `PLAN`, `SOLUTION` 누락을 대체로 올바르게 잡았다.
- 모델 호출 실패, 타임아웃, 스키마 파싱 실패는 100건 동안 발생하지 않았다.

## 5. 개선 우선순위

1. **질문별 메타데이터 검증을 먼저 강화한다.** 정규식만으로 1,446개 질문을 분류한 결과를 그대로 신뢰하지 말고, 질문 문구와 필수 슬롯의 일치 여부를 검사하는 데이터 감사 도구를 만든다. 최소한 `both sides`, `what you do about it`, `compare`, `before/now` 같은 표현은 테스트로 고정한다.
2. **핵심 슬롯에 서버 검증기를 둔다.** `BEFORE_STATE/NOW_STATE`, `ADVANTAGE/DISADVANTAGE`, `PROBLEM/SOLUTION`처럼 구조가 분명한 쌍은 연결 표현과 절 단위 증거를 이용해 LLM 라벨을 교차 검증한다. 단순 부분 문자열 일치만으로 완료하지 않는다.
3. **canonical 슬롯을 UI까지 보존한다.** `DISADVANTAGE`를 일반 `DETAIL` 타입으로만 전달해 의미를 잃지 말고, “반대쪽도 붙여보기”처럼 슬롯별 제목·설명·스캐폴드를 제공한다. `NOW_STATE`, `SOLUTION`, `PLAN`도 각각 전용 문구가 필요하다.
4. **스캐폴드 누락을 백엔드에서 보완한다.** 내용 미션 반환 전 `skeletonKo`와 표현 2개를 검증하고, 부족하면 질문 힌트와 슬롯별 템플릿으로 채운다. 불완전한 공통 fallback을 그대로 노출하지 않는다.
5. **완료 판정을 회귀 테스트 게이트로 둔다.** 조기 완료 0건, 명백한 오프토픽 `TASK_RESET` 100%, 문법 오류 정확도 95% 이상, 내용 미션 스캐폴드 충족 100%를 배포 기준으로 삼는다.

## 6. 결론

슬롯 명칭을 DB·LLM·백엔드에서 통합한 방향은 타당하며, 문법 오류와 명시적 질문 의무에서는 효과가 확인됐다. 그러나 현재 품질의 병목은 프롬프트보다 **질문→필수 슬롯 분류의 누락**, **LLM 슬롯 증거에 대한 의미 검증 부족**, **canonical 슬롯을 UI 미션으로 축약할 때의 의미 손실**이다. 다음 개선은 프롬프트 문구 추가보다 이 세 경계를 먼저 보강하는 것이 효과가 크다.
